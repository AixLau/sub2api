# v0.2.2 Selection Review

This review compares upstream tag `v0.2.2` with the selected product integration
and its current Spark changes. Local origin is not a reason to retain code.
Prefer the implementation that satisfies the actual product contract with
correct behavior, fewer independent mechanisms, and regression evidence.

## Decisions

| Area | Selection | Reason |
| --- | --- | --- |
| Moderation | Combine upstream admission with local semantic review | Upstream model allowlists are a hard admission rule. Local evidence extraction, semantic review and non-punitive provider-error handling cover requirements that keyword/API moderation alone does not. Keep the shared gateway registration and avoid parallel forwarding paths. |
| Billing | Upstream observation and accounting mechanics, local explicit price policy | Preserve outbound and observed service tiers separately and resolve the bill centrally. Keep configured local Fast rates and currency rules; they are product policy, not competing algorithms. Retain request-time DeepSeek costs and rejection of unknown model prices. |
| Payments | Upstream fulfillment core with local provider adapters | Retain transactional/idempotent fulfillment and its separation from public redeem rate limits. Keep NinePlus/HaozPay and multicurrency rules because the product uses those contracts. Do not replace the entire payment implementation to gain an unrelated upstream fix. |
| Public transit | Local public DTOs over the shared Monitor V2 service | Reusing the existing aggregation and error policy avoids divergent statistics. Explicit public DTOs and public-group filtering prevent internal IDs or exclusive groups from becoming public implicitly. |
| Spark moderation | Local entitlement/quota guards over the shared scheduler | Filter ineligible credentials before scheduler candidate limits, resolve shadow credentials through their owner, and retain model-specific quota isolation. A model mapping alone is not proof of the configured Pro-only eligibility. |
| Codex forwarding | Upstream account identity and plugin transport with local tracing/UA policy | HTTP and WebSocket must derive account-scoped identity consistently, and enabled plugin bindings must be respected across forwarding modes. Keep local request tracing and configured outbound User-Agent behavior around those mechanisms. |

## Corrections Implemented

1. Several HTTP response paths and the WS-to-HTTP bridge discarded the
   response's `service_tier`, although the shared result type and native WS
   already separate requested and observed tiers.
   Restore `UpstreamResponseServiceTier` so the shared billing resolver can
   lower API-key billing. Keep the outbound tier until that resolver runs;
   Codex OAuth default echoes and responses claiming a higher price must not
   silently change the bill.
2. Native/passthrough, Messages, Chat and standalone search omitted upstream account identity
   preparation, metadata namespacing and header projection. Restore those
   calls before optional local fingerprint overrides, preserving the original
   native prompt-cache key so header construction does not namespace it twice.
3. HTTP forwarding and WS-to-HTTP bridge paths called the transport directly,
   bypassing the upstream plugin dispatcher. Use the existing dispatcher inside
   the local `DoOpsUpstream` wrapper or endpoint-specific request timing.
4. Restore the Chat adapter's outer response-body assignment and final outbound
   tier extraction so normalization actually reaches the wire and accounting.

The two bridge tests that expected forwarding itself to overwrite the requested
tier are updated to check both recorded tiers and the subsequent billing
resolution. The identity regression uses the production typed API-key context.
Plugin regressions exercise five forwarding paths with an unavailable
enabled binding and require that no direct upstream request escapes it.
Cross-protocol stream/buffer regressions exercise API-key tier downgrades.
Two older assertions are aligned with the existing explicit reasoning-effort
configuration and local 2.5x Fast pricing policy; those business rules are unchanged.

## Scope

The public-transit decision concerns the registered discovery and snapshot APIs.
The unregistered legacy frontend view still describes a different snapshot
contract and is not evidence of a working public page. This review does not
introduce a new public-page workflow or restore that obsolete API contract.

No price multiplier, payment provider, moderation rule or Spark eligibility
policy is changed solely to match upstream. No production deployment or push
is included.

## Verification

- Isolated review base: `3be0d1ac6`, with the changes described above.
- Selected service regressions: 1,574 top-level tests passed, 2,890 passing
  events including subtests, without a skip/exclusion list.
- Coverage includes all observed-tier paths, credential identity, plugin
  forwarding, local billing, payment/redeem, public transit, semantic review,
  Spark scheduling and quota, model allowlists, and WebSocket/passthrough cases.
- The three WebSocket failures documented in the initial integration are
  resolved by the identity fix and the bridge's explicit observation/billing
  contract tests. The initial integration record remains historical evidence.
- Focused handler and route tests for failover, Astra, model allowlists and
  public transit passed.
- The current branch builds with embedded assets and the project's `-s -w`
  release linker flags. An earlier debug-symbol build exhausted local disk
  space during linking; no source failure was involved.
- Unrelated concurrent moderation-candidate and input-budget changes are
  preserved separately rather than included in this patch.
