## 确认的根因

- 314 条同类错误集中于两个账号：66 条和 248 条。代表记录为 #489952、#490624。
- #490624 的完整请求日志重组后通过 SHA-256 校验。61 个 function 历史参数均为有效 JSON；其中 input[166] 的参数包含两个 UTF-16 surrogate 转义，组成非 BMP Unicode 字符。日志显示插件 0.6.10、`attempt=0`、`upstream_status=0`，即发出上游 HTTP 请求之前已经拒绝。
- 旧实现 `formatFunctionPayload` 用 `yaml.Unmarshal` 读取原生 JSON arguments。JSON 支持 `\ud83d\ude80` 这样的代理对，而所用 yaml.v3 扫描器明确拒绝 U+D800–U+DFFF 转义。因此一条有效历史记录即可让整个后续对话持续失败；换账号、重试或调整新生成 YAML 的缩进都不能修复历史数据解析。
- 开始审计时生产安装版已为 0.6.11，处于 disabled。0.6.11 的新调用显式缩进修复不覆盖该 JSON 解码缺陷。

## 0.6.12 修复

历史 arguments 按实际 JSON 契约使用 `encoding/json` 解码，再构建 yaml.v3 节点并交由现有编码器输出。使用 `UseNumber` 保留任意精度数字；对 YAML 会归一化的 CR、NEL、Unicode 行/段分隔符使用库提供的转义字符串输出，避免内容变更。移除直接把 JSON 当 YAML 解析的路径，不添加降级通道，不删除历史，不猜测修补工具内容。

验证包含：旧实现先复现 Unicode 代理对失败；修复后覆盖代理对、JSON 标准孤立代理项解码、字面反斜杠、控制符、特殊换行、嵌套键、数字精度；两种 arguments 外层形式；gRPC JSON/SSE 转发与打包进程重放。

生产明细只在服务器内存中分析，仓库仅保存合成回归与汇总结论，不包含原始请求、授权或用户代码。
