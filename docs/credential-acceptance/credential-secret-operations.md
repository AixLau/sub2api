# Credential secret operations and HTTP bypass audit

This report tracks B5 / AT-36 / AT-40 separately from provider verification. It does not authorize production activation. Real imports remain `UNVERIFIED`, and `gateway.multi_credential_http_enabled` remains false by default. Installation IDs are local identities, not evidence of upstream devices.

## Confirmed defects and changes

1. The prior vault derived fingerprint HMAC and encryption keys from the same master key. Replacing that key would also change token/family aliases and verified subject keys. The new optional `gateway.credential_fingerprint_key` preserves the original derived HMAC key during encryption-key rotation. It does not change existing digests. Initial unrotated configurations still derive the same HMAC as before; after rotation the persisted key-ID record rejects missing or wrong keys at gateway startup.
2. There was no complete offline re-encryption operation. `credential-vault-rotate` now reuses the existing single-host Docker fence, stages a mode-0600 replacement key bundle, and re-encrypts imports, all historical credential versions, unknown refresh compensation, and migration archives in one PostgreSQL transaction. AAD, credential versions, profile/generation, bindings, leases, receipts, unknown states, and fingerprint aliases are not rewritten. Migration 261 stores only key IDs, operation UUID, actor and ciphertext counts. Reusing an operation UUID resolves a confirmed prior commit; failures retain both bundles and leave gateways fenced.
3. An import verifier/provider panic could reach Gin's panic writer, including opaque token text which pattern-based redaction cannot recognize. Import, refresh and the grouped HTTP adapter now consume such panics at their credential boundary, return safe errors, and log only fixed event codes. A refresh with unknown outcome stays blocked; if a new token was received before a completion-store panic, its encrypted compensation is retained. `CredentialSecret` and `CredentialVault` implement safe fmt, slog and zap object formatting. JSON marshaling of the secret is still used internally for encryption and is not a public DTO. Adapter panics after a terminal response but before a returned result are intercepted before lease cleanup, so no missing receipt is misrepresented as complete/zero usage.
4. The legacy raw-refresh endpoint and legacy account create/import/update/bulk/CRS-sync paths accepted a token already registered to a controlled credential instance. They now check server-HMAC aliases before calling the OAuth client or persisting a legacy credential. The guard includes historical access/refresh aliases, aliases retained with unknown refresh compensation, and unconsumed imports, returns fixed errors on storage failure, and does not treat an unregistered token as verified or independent provider authorization. The existing grouped coordinator calls the fixed-address OAuth client directly, under family ownership/version control.

### Current AT-40 follow-up

The two internal defects recorded at a212 were dynamically reproduced against PostgreSQL and are addressed by migrations 262/263 and the shared credential-operation arbitration. See [AT-40 arbitration](at40-arbitration.md) and its exact candidate evidence. History ownership is retained separately from active/UNKNOWN claims; legacy account writes and controlled activation share a transaction protocol; raw refresh records a durable operation before network I/O. This does not provide real provider identity or compact proof and does not permit production activation.

The prior four-class vault now also re-encrypts the fifth legacy-refresh result class. Legacy OAuth refresh requires a configured vault even with the HTTP grouping flag off; an expired cached refresh result is not automatically replayed. The new report specifies these operational changes and fencing/rollback requirements. Earlier test results below remain historical and do not cover later code.

### Historical a212 finding: concurrent legacy/control admission (superseded by AT-40 arbitration)

Static control-flow inspection identifies an actual TOCTOU gap, not merely an unrun test: the legacy guard's SELECT and the later `accountRepo.Create/Update` (admin import/edit/bulk and CRS sync), or the raw OAuth network call, do not share a lock/transaction with `PutImport` and controlled activation. A legacy caller can observe no alias, a concurrent controlled import can then register it, and the legacy write/call can subsequently proceed. The deterministic tests prove rejection of **already committed** known aliases; they do not close concurrent cross-entry registration. AT-40 remains PARTIAL. No whole-account repository transaction redesign was included in this targeted change.

A concrete interleaving is: (1) request L runs the legacy alias SELECT and observes no registered match; (2) request C commits `PutImport` for the same token and subsequently activates its controlled instance; (3) L continues into `accountRepo.Create/Update`, or the OAuth client sends its refresh request. There is no shared token-scoped lock between steps (1) and (3), so the earlier check cannot reject C's later registration. No test claiming concurrent cross-entry serialization was run. This remains an internal production blocker independently of missing provider verification.

A second conditional static gap remains: unknown refresh compensation inserts new fingerprints with `ON CONFLICT DO NOTHING` to preserve an existing owner and encrypted result. The legacy guard intentionally excludes retired-to-legacy instances for drained rollback. If a new active instance's unknown result collides with a historical alias owned by a retired instance, that alias still belongs to the retired owner and may be omitted by the guard. This cross-retired collision case has not been run; the passing rotation/alias test covers old/latest/pending aliases belonging to the same controlled instance. Do not generalize it to every possible provider token collision.

The second sequence is: (1) fingerprint F exists on retired instance R after a safe single-instance rollback; (2) the provider returns token T with F during active instance A's refresh, but its normal completion fails; (3) `MarkCredentialRefreshUnknown` durably stores A's encrypted result and cannot replace F's existing unique owner R; (4) a legacy check for T excludes R because it is retired. This sequence is inferred from the SQL and requires a cross-retired token collision; it was not observed against any provider and was not dynamically reproduced. It remains a conditional internal production blocker until rejected or safely represented without losing the encrypted compensation. The regression does prove no mutation of existing owners, no replacement of newest token snapshots, and preserved UNKNOWN occupancy for the ordinary noncolliding path.

The legacy alias guard is a check of records already durably registered at lookup time. It is not a general proof that independently imported legacy tokens belong to a different provider family, and it does not add a cross-system atomic transaction over arbitrary legacy authorization/import operations. Unknown family relationships remain an external-contract limitation, not permission to mark an import `VERIFIED`.

## Offline rotation and rollback procedure

- Keep the HTTP feature disabled. Ensure every gateway/background writer is in the exact managed Docker Compose service; unmanaged processes, privileged/host-network containers and a lost inventory block this operation. This command does not operate on remote hosts.
- Create a mode-0600 JSON current-key bundle containing `credential_vault_key` and, if already separated, `credential_fingerprint_key`. Create a separate mode-0600 file for a newly generated 32-byte hex encryption key. Do not put keys into flags, tracked files, logs or support packages.
- Build `./cmd/credential-vault-rotate`, then run with `--current-keys-file`, `--new-encryption-key-file`, `--staged-keys-file`, `--actor`, stable `--operation-id`, `--compose-project` and `--gateway-service`. The DSN uses `SUB2API_CREDENTIAL_CONTROL_DSN`. Staging completes and fsyncs before any database change. Existing staged files must match exactly.
- The command fences the identified gateway service, re-encrypts all four secret classes, verifies the fence again and commits the key-ID record/count-only audit event. It does not reconnect/start containers or enable the feature. Install BOTH values from the staged bundle into the credential configuration while containers remain fenced.
- If any call reports failure or the commit is uncertain, retain old and staged bundles, keep containers fenced, and retry the same operation UUID. Never restore a database snapshot to undo rotation. A partial transaction does not become a successful rotation record.
- A controlled reverse rotation is a new operation that decrypts the CURRENT data with the new key and re-encrypts the CURRENT data with the retained old encryption key while keeping the fingerprint key fixed. It preserves the newest refresh token and encrypted unknown-result compensation. It is not restoration of an old token/archive snapshot.
- Do not run an old binary which lacks the persisted key-ID check after a rotation. Migration 261 is forward-only. The state record remains during rollback so misconfigured gateways fail closed.

## Explicit limits

The rotation approach keeps application identity separate from re-encryption, consistent with the distinction between rewrap and token rotation in [Vault Transit](https://developer.hashicorp.com/vault/docs/secrets/transit). Diagnostics use fixed, nonsecret fields in line with [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html). Existing Go AES-GCM, HMAC, sql transactions and logging interfaces were reused; no encryption library or APM SDK was added.

The offline CLI's fence inherits the declared single-host inventory boundary. It cannot fence an external executor, a Docker administrator who deliberately reconnects nodes, or a credential already used outside this deployment. A genuine encryption-key compromise is not fully remediated merely by retaining a formerly derived fingerprint HMAC key; independent keyed-digest-key compromise requires a separate alias/identity migration, not a silent rehash. External APM/body capture, heap/core dumps and hostile process-memory readers are outside the in-repo canary tests. Secrets are necessarily decrypted in process memory to make an authorized HTTP request. These limits are not grounds to bypass `UNVERIFIED`, release `UNKNOWN` capacity, or replay upstream work.
