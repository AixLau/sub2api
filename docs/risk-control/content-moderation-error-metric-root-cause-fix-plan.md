# 内容审计异常统计根因修复方案

## 1. 结论

生产环境 `v0.1.163` 的“审核异常”数量主要是统计口径被污染，不是语义审核模型在最近 12 小时内大面积失败。

根因是 `content_moderation_logs.error` 同时承载了两种互斥语义：

- 真正的审核执行错误、供应商错误或提取失败原因；
- 候选命中来源、语义审核 verdict、置信度、策略覆盖等正常审核证据 JSON。

仓储层又把 `error <> ''` 当作异常条件，管理看板直接以该查询结果展示“审核异常”。因此，成功的“语义审核放行”和待复核记录也被统计成异常。

这不是查询层的偶发错误，也不应通过“识别 JSON 并排除”的兼容逻辑处理。必须恢复 `error` 的单一职责，并把审核证据放入独立字段。

## 2. 生产证据

排查时间：2026-07-23，生产管理页面显示版本 `v0.1.163`。

- 近 24 小时看板：审核异常 `4,011`，风险命中 `331`，已拦截 `22`，待人工复核 `856`。
- 近 24 小时语义审核成功调用 `2,847`，主模型调用 `2,789`，备用模型调用 `58`。
- 将记录时间筛选为 2026-07-23 00:20 起的最近 12 小时，全部记录为 `1,206` 条。
- 在同一时间范围选择“异常”结果，仍显示 `1,206` 条。
- 异常筛选结果中可见“语义审核放行”和“语义审核待复核”，其 `error` 内容实际是语义审核元数据 JSON，而不是失败原因。

以上证据说明异常筛选条件覆盖了正常候选审核记录。生产原始提示词和用户标识不纳入本方案。

## 3. 代码证据链

1. 候选语义审核把模型结果组装为 JSON 元数据：
   `backend/internal/service/content_moderation_candidate.go:1384-1411`。
2. 成功、拒绝、待复核等候选结果都经过 `buildCandidateLog`，并把元数据作为最后一个参数传给 `buildLog`：
   `backend/internal/service/content_moderation_candidate.go:1414-1415`、`1449-1458`。
3. `buildLog` 的最后一个参数命名为 `errText`，但无条件写入 `ContentModerationLog.Error`：
   `backend/internal/service/content_moderation.go:4823-4826`。
4. 生产仓储用 `l.error <> ''` 定义“异常”：
   `backend/internal/repository/content_moderation_repo.go:726-736`。
5. 看板的异常卡片调用 `result: 'error'`，并直接使用返回总数：
   `frontend/src/views/admin/RiskControlView.vue:3395-3407`、`2819-2851`。
6. 候选审核重构在 2026-07-13 的 `d3285dd40` 引入了这条元数据写入路径；之后语义候选流量增长，使错误统计污染集中暴露。

## 4. 根因修复设计

### 4.1 恢复日志字段契约

新增独立的 `metadata JSONB NOT NULL DEFAULT '{}'` 字段，并在 Go 模型和 API 中增加对应的结构化字段。

字段职责固定为：

| 字段 | 允许内容 | 空值规则 |
| --- | --- | --- |
| `error` | 真实执行失败、供应商错误、提取失败、持久化失败原因 | 成功、放行、拒绝、待复核必须为空 |
| `metadata` | 命中来源、候选规则、语义模型输出、策略覆盖、证据版本等审核事实 | 无附加元数据时为 `{}` |
| `action` | 最终审核处置 | 不承担错误统计职责 |

实现要求：

- 将 `buildLog` 的 `errText string` 改为明确的 metadata 参数，禁止再通过位置参数传递元数据。
- 所有成功/放行/拒绝/待复核路径只写 `metadata`，不得写 `error`。
- 所有失败路径显式设置 `error`，并保留可分类的失败原因；失败元数据仍放在 `metadata`。
- `error` 不存模型 JSON、不存候选证据、不存正常审核结果。
- 不把旧 `error` 字段改名后继续混用；要从类型和构造函数入口阻断再次误写。

### 4.2 统一统计口径

修复数据契约后，异常查询继续使用 `error <> ''`，不增加 JSON 解析、前缀判断或历史格式兼容分支。这样新写入和历史修复后的数据都遵循同一个可验证规则。

需要明确纳入异常的情况：

- 普通内容审核 API 调用失败；
- 语义审核节点不可用、证据不完整且按失败策略落日志；
- 本地提取、配置读取或审核持久化失败。

“语义审核放行”“语义审核拒绝”“待人工复核”“策略降级但审核成功”不属于异常。若业务需要区分“审核处置失败”和“策略待复核”，应使用 `action`/`review_status` 单独统计，不能复用 `error`。

### 4.3 API 和前端同步改造

- API 返回 `metadata`，前端 `semanticReviewOutput` 从 `row.metadata` 读取，不再解析 `row.error`。
- 审核详情页将“错误原因”和“审核证据”分成两个区块；错误为空时不显示错误区块。
- 看板异常卡片保持真实失败定义，记录列表的“异常”筛选与卡片总数必须来自同一仓储条件。
- 候选规则动作与最终审核处置继续分开显示，避免出现“最终放行但候选规则动作是拦截”时被误认为系统异常。这是展示语义澄清，不改变审核决策。

## 5. 历史数据修复

新增一次性、可审计的数据迁移，不在运行时增加兼容判断。

迁移步骤：

1. 先增加 `metadata` 字段和索引/约束，部署新代码，禁止回滚到仍会把元数据写入 `error` 的旧版本。
2. 对历史记录逐批扫描：仅处理能解析为 JSON object、包含已知审核元数据键，且没有明确失败原因的记录。
3. 将原 JSON 复制到 `metadata`，把 `error` 清空；真实错误文本、失败原因和非审核 JSON 错误保持不变。
4. 每批记录迁移数量、跳过数量、失败数量和校验摘要；迁移前后总行数、失败行数、非空 metadata 行数必须可对账。
5. 迁移完成后重新计算近 24 小时和近 12 小时异常数量，并抽样核对放行、待复核和真实失败三类记录。

迁移不能使用“所有合法 JSON 都是元数据”的宽泛规则。必须通过已知元数据键和失败字段规则判定，无法确定的记录进入待人工确认清单，不得静默清空。

## 6. 测试与验收

### 后端

- `buildLog` 单测：传入 metadata 后 `Error == ""` 且 metadata 完整保留。
- 候选语义审核 allow/review/reject 单测：metadata 非空，Error 为空，Action 与 Flagged 保持原语义。
- 真实错误路径单测：Error 非空，metadata 可选，仍能被异常筛选命中。
- 仓储集成测试：metadata-only 记录不进入 `result=error`；真实错误记录进入；`result=pass` 不包含错误记录。
- 历史迁移测试：元数据 JSON、真实 JSON 错误、普通文本错误、空值四类样本分别得到预期结果。

### 前端

- 审核详情从 `metadata` 渲染模型输出，`error` 只渲染失败原因。
- 异常卡片、异常筛选和分页总数使用同一结果集。
- 放行记录、待复核记录不得出现在异常筛选中。
- 候选动作和最终处置显示可区分，文案不再把候选动作当作最终结果。

### 生产验收

执行只读对账：

```sql
SELECT
  COUNT(*) AS total,
  COUNT(*) FILTER (WHERE error <> '') AS real_errors,
  COUNT(*) FILTER (WHERE metadata <> '{}'::jsonb) AS with_metadata
FROM content_moderation_logs
WHERE created_at >= NOW() - INTERVAL '12 hours';
```

验收标准：

- 最近 12 小时“异常”总数等于 `real_errors`，不再等于全部候选审核记录数。
- 任意 `semantic_review_allow` 记录的 `error` 为空，metadata 中保留完整审核结果。
- 任意真实失败记录的 `error` 非空，并能在异常列表中定位失败原因。
- 24 小时看板、结果筛选、详情页三者数量和字段语义一致。
- 新代码路径和数据迁移相关测试全部通过；不得通过放宽筛选条件或隐藏异常来降低指标。

## 7. 发布顺序与回滚边界

1. 先提交 schema migration、模型/仓储/服务/前端改造及测试。
2. 生产执行 migration 后立即发布修复版本。
3. 发布后先做只读对账，再执行历史数据迁移。
4. 历史迁移完成并验证前，不允许切回旧版本；旧版本会重新污染 `error` 字段，不能作为回滚方案。
5. 若新版本审核决策本身出现问题，回滚前必须保留新字段和停止旧写入路径；回滚决策逻辑不等于回滚字段契约。

本方案的修复对象是错误字段的职责混用。不得用“把 JSON 错误排除”“前端隐藏异常卡片”或“只修改 24 小时统计 SQL”等方式做表面兼容。
